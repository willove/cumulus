# 失效模式规约：这四类错，装配能力时反复发生

> 这不是教训总结，是**可查的规约**。四类错都在 2026-10 的几轮里**连续发生**，
> 而且都不是逻辑错——是**接线错**：代码能编译、测试全绿、读数看起来正常，
> 只有真跑才显形。每类现在都有一道机械门禁或结构约束。

## 判定标准

一个失效模式配一条规约，必须满足其一：

- 有**测试/门禁**能拦住它（`internal/arch`、`internal/qaflow/wiring_test.go`、
  各 stage 的 Verify）；
- 有**结构约束**让它写不出来（如"能力必须在接线处显式声明"这类签名约束）。

只有文字、没有牙齿的条目不进这里——**不能验证的规约等于没有规约**。

---

## 一、可选面互相挡掉

**症状**：读数是 `enabled=true, applied=false`（"装了却不工作"）；或某个臂"触发了 N 次、
某能力零次"。

**真例**（三个）：

1. `escalateFn` 只在级联臂装配 → 单臂"升级触发 10 次、词汇桥一次没走"
   （`internal/qaflow/trace.go` 的 `EscalateStage{Retrieve: …, Expand: …, Weighted: …}`）。
2. `traceFunc` 早退 `if em == nil { return nil }` → 把**窗口分级器**一起挡掉
   （`/v1/qa` 不装 emitter，只有 `/v1/qa/stream` 装）。
3. 桥住在 `escalateRetrieve` 里，而零窗口在**路由**就 `refuse` → 最需要桥的情况
   （词面全落空）永远走不到桥。

**规约**：

- 早退条件写成"**我要用的东西**都不存在"，不写"某一个不存在"：
  `if em == nil && WindowClassifier == nil` 而不是 `if em == nil`。
- 可选件的装配**不绑在别的臂/别的面上**：桥、分类器装不装与"测不测级联""走不走
  stream"无关。
- **门禁**：`internal/qaflow/wiring_test.go` 的
  `TestEveryOptionalCapabilityActuallyRuns` —— 所有可选面一次全开，逐个断言它
  **真的产生了效果**（事件/挂点/记录）。写不进断言的面不进这道门。

## 二、往"还没写的记录"里写读数

**症状**：结局字段**恒空**（不是偶尔空，是每次都空）；代码 review 看不出问题。

**真例**（两个，同一个坑）：

1. 桥的结局写进 `EscalationRecord`，而 `escalateRetrieve` 跑在
   `context.Set(KeyEscalation, …)` **之前** → 那条记录当时还不存在。
2. 窗口分级的结局写进同一条记录，分级发生在升级之前 → 同一坑。

**规约**：

- **观测状态住在生产者自己的挂点上**，不寄生在别人稍后才写的记录里。
  挂点形状：`WindowClassResult{Classes, Outcome, Ran}` ——**三态同址**
  （没跑 / 跑了失败 / 跑了成功），不写就分不出来。
- 要往别人的记录里追加字段时，确认写入时机**在**那条记录被 set **之后**；否则换挂点。

**门禁**：`wiring_test.go` 断言"分级结局恒非空（ok/failed/skipped 任一）"。

## 三、方法值把能力丢掉

**症状**：流式/分级/桥"装配了却走整条老路"；`applicable` 类字段为 false。

**真例**：`l.Synthesize` 是**方法值**，传进 `Options.Synth`（函数类型）之后
`SynthesizeStream` 这个方法**在类型层面不存在了**，断言永远失败。

**规约**：

- **能力在接线处显式声明**，不靠运行时从接口断言里捞：
  `Options.StreamSynthFunc`、`Options.WindowClassifier`、`Options.Decision` 都是
  显式字段；上游不支持就**不接这条腿**（免得"接了但每步都退回调"，读数却显示
  能力开着）。

## 四、装配状态只在出错时可见

**症状**："它到底装没装"无从判断——四轮排查里三次在猜这件事（语料？开关？装配？）。

**真例**：`bridge: 无 LLM，桥缺席` 只在 `err != nil` 时打印，于是"桥压根没装"
**没有任何输出**。

**规约**：

- 装配状态**无条件可见**：`已装配(model=…) / 已关(开关) / 缺席(原因)` 三态都打。
- 能力探测结果进**读数**（`classification.{enabled,applied,outcome}`），
  不只进日志。

## 新增能力时的自查（照着走一遍）

1. 我这个能力的"效果"是什么**可观测的东西**？（事件/挂点/记录——没有就说明还没法验证）
2. 它的早退条件是什么？会不会**顺带挡掉别的可选面**？
3. 我的读数写在哪个挂点？那个挂点**在写入时机之前存在吗**？
4. 能力是**接线处声明**的，还是靠运行时断言捞的？
5. 装配状态在**没出错**的时候也看得见吗？
6. `wiring_test.go` 里加了断言吗？（加了才算是被门禁保护）

六问里有任何一条答不上来，就先补上再提交。

## 第五类：把"文档内定位"的信号拿去"文档间排序"（试过，无效，已撤）

**场景**：真实法律语料（1548 篇）问"劳动合同应当采用书面形式"，《劳动合同法》被
《招标投标条例》《旅行社条例》挤出 top-9（**金标 top1 只有 4/10**）。

**试过的办法（不含词典）**：给 BM25 叠一个"**长片段加成**"——查询里相邻二元组能拼出更长的
连续片段（"劳动合同"4 字），片段越长越罕见、越有区分力，命中文档按 `(len-1)²` 加权。
看起来完全通用：纯几何、不依赖任何领域词典。

**实测结果：有害。** top1 从 **4/10 降到 3/10**。逐问量下来，原因很清楚：

```
金标加成 14.57 vs top1 文档加成 14.57      ← 完全相同
金标加成 16.07 vs top1 文档加成 16.07
```

**为什么**：每部法律都满是法律套话（"合同应/用书面/应当采用"），**片段连续性能区分
"文档里的哪一条"，区分不了"哪一部法"**。而且加成大多顶到 50% 上限——**上限一触发，所有
文档拿到同样的相对提升，等于没有区分**，只是把噪声放大了。

**留下的结论**：
1. **片段连续性是"文档内定位"的信号，不是"文档间排序"的信号。**
   它在窗口选择（超长文档按"新增覆盖"挑互补窗口）里确实有效，已保留在 `windowSpans`。
2. **排序里任何加权项都必须量过再留**——没量的加权项比不加更危险：它看起来在做事，
   实则把噪声放大，且**上限机制会掩盖它无效的事实**。
3. 代码已删（只留结论）。一个没有调用方的"优化"留在仓库里，下一个人会以为它有用。

**还欠着的问题**：top1 4/10 是**词面检索在专业语料上的天花板**（"合同"命中所有含合同的
法律）。它在**文档级**，不在窗口级。真正的解法是语义检索或术语发现（无监督、语料自驱动），
而语义检索组件**我们还没有在真实规模上测过**——在那之前，谁都不该说它能解决这个。
